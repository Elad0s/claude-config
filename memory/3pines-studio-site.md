**Yoast Premium indexables are a write-through cache — the #1 gotcha.** Writing `_yoast_wpseo_*` post meta or the `wpseo_taxonomy_meta` option directly bypasses Yoast's save hook, so `wp_yoast_indexable` keeps serving the OLD title/description on the front end even after cache purges. Always `UPDATE wp_yoast_indexable` to match (or re-save through the UI), then purge. Verify against the origin with `curl --resolve 3pines.studio:443:147.93.74.187` to rule out Cloudflare.
WP Rocket has no CLI here — purge with `wp eval 'rocket_clean_domain();'`. Elementor: `wp eval '\Elementor\Plugin::$instance->files_manager->clear_cache();'`.

**Creating WPCode snippets via WP-CLI — two blockers, both non-obvious.** (1) `wpcode_block_unauthorized_snippet_writes` (in `insert-headers-and-footers/includes/post-type.php`) hooks `wp_insert_post_empty_content` and rejects any `wpcode` insert when the current user lacks `wpcode_edit_snippets` — WP-CLI has no user, so it fails with the misleading "content, title and excerpt are empty". Run `wp --user=2 …` (elad oren, admin). (2) WPCode also filters `post_content` on save, so insert a placeholder and write the real code with `$wpdb->update`. (3) The snippet then still won't execute until you call `(new WPCode_Snippet($id))->rebuild_cache()` — deleting the `wpcode_snippets` option is NOT enough. Required meta to match existing snippets: `_wpcode_auto_insert=1`, `_wpcode_auto_insert_number=1`, `_wpcode_priority=10`, plus terms `wpcode_type=php` and `wpcode_location=everywhere`.

**RTL bidi fix for the brand (snippet 8364, "RTL: isolate 3Pines brand in titles").** Unicode treats the leading `3` in "3Pines" as a European Number, so in Hebrew titles the bidi algorithm detaches it and renders `... שמביא מטופליםPines | 3`. Snippet filters `wpseo_title`, `wpseo_opengraph_title`, `wpseo_metadesc`, `wpseo_opengraph_desc` and `wpseo_twitter_description` to insert U+200E (LRM) before `3Pines`. Covers all 51 titles + the 13 descriptions that carry the brand, centrally, and survives per-page edits. **Rule for new copy: never start a Hebrew title or description with the Latin brand** — put it at the end (titles) or mid-sentence after a Hebrew word (descriptions); the LRM is a safety net, not a licence. Caveat: the fix is output-side only — Yoast's snippet **preview inside wp-admin still renders scrambled**, that's cosmetic.

Original diagnosis, for context:
**Consent Mode v2 was NOT implemented.** `googlesitekit_consent_mode` is `{"enabled":false, regions:[EU/EEA only — no IL]}`, and on a fresh visit the dataLayer shows **no `gtag('consent','default',…)` at all**: order is `js` → `config GT-TWMXNSQ8` → `config G-XEBQB9SZVB` → (index 11) `consent update: denied` from CookieYes. Consequence: gtag treats the initial state as granted, so the first `page_view` and the `_ga` cookie go out *before* the banner is answered (a compliance exposure under Amendment 13 — he has a `/privacy-law-13/` post), while every interaction fired *after* the banner is dropped unless the visitor accepts. That is exactly the observed page_view-yes / contact_click-no split.
Behavioral modeling is a dead end here regardless: GA4 needs ~1,000 daily users for 7 of 28 days; this site does ~150 sessions per 90 days, three orders of magnitude short. Don't chase it.
